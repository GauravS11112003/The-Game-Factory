# D-1: lane D platform decisions that other lanes rely on, and two contract asks

Lane D · Mind & Platform. Status: open (owner to record the accepted items in `docs/v2/CONTRACTS.md`).

## 1. Deviation: published v2 levels live in `levels_v2`, not in v1's `levels`

**What.** `vision/app/db_v2.py` adds a table `levels_v2 (id, version, …, json, level_hash, …, PRIMARY KEY (id, version))`.
v2 games are rows of the shared `games` table with `format = 2` and `rules_json`, as §11.3h says.
Read helpers fall back to v1's `levels.json_v2`, so levels migrated in P4 are still found.

**Why.**
- `GET /api/v2/levels/{id}?version=` needs version history. v1's `levels.id` is a primary key, so it cannot hold
  several versions of one level.
- v1's home feed and remix tree read every `levels` row of a game as a v1 `Level`:
  - `list_games_with_counts` builds the cover from `json`;
  - `thumbnailFor` reads `level.source.backdrop_url`.
  A v2 row there would crash the live v1 home page. D25 says v1 must keep running until P6.
- Today v1 shows a v2 game as a game with no levels. That is harmless.

**Affects.** D only until P6. At P6 the v1 aliases read `levels_v2`.

## 2. Ask to lane B: the meaning of `BindEnemy.speed` for timing archetypes

The sanitizer maps model speed enums to numbers through `shared/spec/params.json` `GRIDS`:
- `move` → `platform_speed`;
- `saw` → `saw_speed`;
- `enemy`, chosen by archetype:
  - walker and static → `walker_speed` (c/s);
  - flyer → `flyer_speed` (c/s);
  - chaser → `chaser_speed` (c/s);
  - hopper → `hopper_interval` (s);
  - shooter → `shooter_interval` (s);
  - crusher → `crusher_warn` (s).

So for hopper, shooter and crusher, `speed` carries that archetype's timing value in seconds. Please interpret it
this way in `mergePerception`, or tell D which other mapping you want. The change is one table in
`vision/app/mind/sanitize.py` (`ENEMY_GRID`).

## 3. Ask to lane B: a `target` param on `parse_rules`

A rule typed while a stroke is selected binds to exactly that component (§3.3). The bridge sends
`parse_rules {text, graph, target}`, where `target` is a component id or null. Today `dispatch.ts` ignores the extra
key. Please pass it to `parseRules`.

## 4. What D sends to the core, and what D expects back

- **`build_tiers` edits.** D sends only the *intent* records:
  - U edits from perception, the keyword parser and the kid;
  - K edits;
  - suggestions the kid accepted;
  - every record whose status the kid toggled (`applied` or `undone`).
  The core regenerates N, R and greedy P/C edits itself, and honours statuses by stable id.
- **`build` edits (publish recompute).** D sends that tier's stored records with the kid's statuses, plus the intent
  records. The browser must do the same, so the two `level_hash` values match.
- **Typed rules.** They are parsed one sentence at a time. When the model's binding evidence covers a sentence, or
  binds its target, that sentence's parser edits are dropped at Understood (§3.3 merge 5).
- **Suggestions.**
  - `EditRecord.cid` should be set on edits that come from a menu candidate. An accepted suggestion is re-applied
    as a pick by cid while the current menu still offers it.
  - `apply_plan` should return `rejected: [{cid, why}]`.
- **Ask options.** An `AskOption` may carry the extension key `x_statuses: {edit_id: "undone"}`. The `keep_or_fix`
  "Keep it" answer uses it. The server applies it.
- **Answers.** For a "Tap it" ask, `choice` may be a tapped object id (`o12`). Placeholders `"$tap"` in a tap
  option's ops are replaced by that id. If there are no ops, `which_door` becomes `link {key: about, door}` and
  `which_flag_is_goal` becomes `set_role goal`.

## 5. What lane F can rely on

- **Draft files.** They are served under `/uploads/drafts/<draft_id>/`:
  - `ink.json` (the `ink_ref` of tier events);
  - `tiers/<stage>.<tier>.json`;
  - `tiers/current.<tier>.json`, the authoritative tiers after `PUT edits` or `POST answers`. Those endpoints return
    only the `TierSetSummary`.
- **Event streams.**
  - Redesign and "Why is this hard?" builds append to the same draft `events.jsonl`, so seq stays monotonic per draft.
  - `GET /builds/{id}/events` starts at that build's first event and ends at its `done`.
  - A build killed by a reload is closed with a fatal `error.build_failed` and `done`.
- **Accepting suggestions.** To accept one, send `PUT edits {statuses: {<suggested id>: "applied"}}`. Sending
  `"undone"` on the same id makes it a suggestion again.
- **Redesign and critic conflicts.** `POST redesign` and `POST critic` answer **409 `warning.design_late`** while the
  first build has not reached Designed yet. After Designed they cancel its late-suggestion wait.
- **DESIGN timing.** DESIGN is asynchronous (P0 bakeoff). The Designed tiers are greedy unless the speculative plan
  is already back when Understood lands. The model's validated picks then arrive as `suggestions`, followed by a
  `note` with `source: "model"`.
