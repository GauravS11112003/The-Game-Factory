# F-4: how the P5 screens use lane D's wave-2 API (lane D)

Lane F · Studio. Status: open. Client code: `web/src/app/api.ts`. This follows D-2 §2; anything below that differs
from what D shipped is an ask. Where a route fails with 0/404/405/501/503 the UI either shows the sentence for the
error key or runs the same job in the browser core (noted per route).

## Game rules (§8.2) — `web/src/app/screens/rules.ts`
- **Save for new levels:** `PUT /games/{id}/rules` (no query).
- **Apply to all levels:** the client first calls `POST /games/{id}/rules/check` (rows' `x_title` are shown). On a
  failure it runs the same dry run in the browser core with lane B's `rulesCheck` helper, so both list the same
  levels with the same reason keys.
  - Nothing breaks → `PUT ?apply=all`.
  - Something breaks → the list is shown and the change is blocked. "Let the designer fix them" shows the Faithful
    repairs per level (the server check carries no repair sentences, so these come from the browser core's
    `rulesCheck(..., {repair: true})`). Only when every level is repairable does "Save and fix them" send
    `PUT ?apply=all&repair=1`.
  - A `409 rules.blocked` is read from the body's `affected` and shown the same way.
- **Rules Sheet:** `POST /scan/rules-sheet` (multipart `photo`). The patch fills the boxes on screen and the kid
  saves; `asks`, `x_warnings`, `story` and `game_id` are shown. A sheet whose `game_id` names another game is refused.
- **Ask:** please return the per-level Faithful repair sentences from `rules/check` too (`repairable`, `repairs` as
  lane B's `AffectedLevel` now allows), so the server path needs no browser dry run.

## Library (§8.1) — `web/src/editor/creature.ts`, `web/src/app/screens/library.ts`
- Creature Studio: `POST /library/interpret`; on any error the client's keyword reader
  (`web/src/app/creature_words.ts`) pre-selects the chips and says so.
- New versions: `POST /library/{id}/versions` (the full type), falling back to `POST /games/{id}/library` with the
  same id.
- "Update levels to vN": the browser core dry-runs it first (every level pinning an older version is rebuilt with the
  new version and re-verified), then "Update n levels" calls `POST /library/{id}/update-levels?v=`; `updated` and
  `broken` are listed.
- Library Sheet: `POST /scan/library-sheet` (multipart `photo`, plus `game_id`). Each draft is shown with its own art,
  name (editable; the placeholder is "Creature N" when `name_source` is `default`), what it does, its asks and
  warnings, and is saved as a full `LibraryType` through `POST /games/{id}/library` (or reopened in the studio).
- Instance art: the preview's "Use my new drawing" sends a kid edit `use_library` with the extension key
  `x_own_art: true` (lane B's `apply.ts` honours it); "Use <name>'s drawing" sets that edit to `undone`.
- PDFs (`/api/v2/templates/library.pdf?game=`, `/api/v2/templates/rules.pdf?game=`, pack PDFs) are fetched before
  opening, so an error shows a sentence.

## Prompt-to-level (§8.3) — `web/src/app/screens/prompt.ts`
- `POST /prompt-levels` → the preview follows the build; "Back to drawing" builds the editor document from the
  draft's `ink` (draft strokes keep `origin: "draft"`). While the route fails, the browser core runs `keywordPlan` →
  lane B's `generateLevel` (layout, bot proof, deterministic fixer) and opens the draft straight in the editor.

## Paper packs (§6.4) — `web/src/app/screens/scan.ts`
- `POST /packs` → the pack is remembered on the device and its `pdf_url` opened (fallback
  `/api/v2/templates/pack/<id>.pdf`). `#/scan?pack=<id>` reads `GET /packs/{id}` for k when this device didn't print
  it. Single plain sheet: v1 `GET /api/templates/blank.pdf`.
- `POST /builds` from the tray: `photos` in sheet order (`sheet<n>.jpg`), `pack_id`, `game_id`, `parent_id` (remix
  and extend packs). The tray reads QR codes in the browser when it can (`BarcodeDetector`); the server stays
  authoritative.

## Runs (§8.4) — `web/src/app/screens/play.ts`
- Boards: `GET /levels/{id}/runs?board=any|collector&limit=10`; `creator` and per-row `older` are used.
- Before `POST /levels/{id}/runs` the browser core re-simulates the replay with the claim (`verifyRun`); a run that
  can't check out shows `run.rejected` without the round trip. Runs that used the checkpoint rewind are never sent.
- `?vs=<run>`: the level is loaded at `run.level_version`, the challenger's numbers come from re-simulating the
  replay, and the ghost gets `kind: 'challenger'` and `sprite_url`.

## Export / import (§8.5)
- "Download" on the play screen: `GET /levels/{id}/export?version=`; "Download game" on the game page:
  `GET /games/{id}/export`; "Open a file" on the home page: `POST /import` (multipart `file`) → goes to the game, or
  the first level.
